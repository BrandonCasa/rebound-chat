# ADR 0001: AWS-Native WebRTC Platform Baseline

## Status

Accepted for implementation scaffolding.

Superseding planning direction as of 2026-05-13: MongoDB, GridFS, Socket.IO, EC2/PM2/Nginx deploys, and HLS-only live assumptions are removal targets. Temporary compatibility paths may exist only to export data, validate parity, or avoid data loss during migration.

## Context

Rebound currently runs a Vite/React/Electron client with an Express/MongoDB backend, Socket.IO realtime, GridFS-backed media storage, and HLS live streaming generated by FFmpeg on the broadcaster. The migration plan in `plans/00-master-plan.md` moves the platform to WebRTC-first live streaming and AWS-native persistence/runtime systems while phasing out legacy systems.

The first implementation work must introduce AWS and WebRTC building blocks without data loss. The existing EC2/PM2/Nginx production deployment can remain only until the AWS deployment path is verified, then it must be retired.

## Decision

The target platform baseline is:

- AWS CDK v2 TypeScript owns cloud infrastructure.
- Development deploys target `us-east-2`; production deploys target `us-east-1`.
- Static web assets are hosted from S3 behind CloudFront.
- Runtime services run on ECS Fargate.
- Aurora PostgreSQL becomes the canonical application database.
- S3 stores media attachments, live HLS fallback/recording artifacts, frontend build artifacts, and deployment bundles.
- API Gateway WebSocket APIs replace Socket.IO after a protocol migration.
- LiveKit is the selected SFU and runs on ECS Fargate with Redis.
- WebRTC live media uses LiveKit directly; Express, API Gateway, CloudFront, and Nginx do not proxy RTP/SRTP media.
- HLS remains available only as a temporary compatibility path until WebRTC health and cutover behavior are proven.

## Media Compatibility Gates

The MVP target is H.264 video plus Opus audio over LiveKit. FFmpeg WHIP ingest is the preferred broadcaster path, but it is gated on the bundled FFmpeg build exposing the WHIP muxer and successfully publishing into a local LiveKit room.

If FFmpeg WHIP fails a gate, the fallback decision is LiveKit-supported ingress or a native Electron WebRTC publisher. The product should not migrate viewers or production deployment onto the new path until that decision is documented with test output.

## Local Development Shape

Local WebRTC compatibility starts with Docker Compose for LiveKit and Redis. PostgreSQL and LocalStack can be added to the same local stack as the data and storage migration begins, but the first local media gate only needs one LiveKit server and Redis.

## Consequences

- Socket.IO cannot be rehosted on API Gateway WebSockets. Client and server message contracts must move to explicit route-keyed JSON envelopes.
- MongoDB and GridFS migration must be staged behind repository boundaries so current routes keep working while Aurora and S3 come online, then MongoDB/GridFS runtime code and dependencies must be removed.
- Live cleanup work must leave the API process before ECS service scaling is enabled.
- LiveKit-on-Fargate needs explicit work for UDP/TCP load balancing, advertised hostnames, TLS, autoscaling, and observability.
- The existing EC2 deployment remains intact only until the AWS dev environment can deploy and roll back repeatably; after that, EC2/PM2/Nginx deployment paths are removed from supported architecture.
